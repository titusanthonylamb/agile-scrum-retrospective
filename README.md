# SNHU Travel Project: Scrum-Agile Retrospective

This repository contains my retrospective on the SNHU Travel project as a Scrum Master. It covers the Scrum roles, how the team handled user stories and a major mid-sprint change, the tools we used, and the strengths and weaknesses of the Scrum-Agile approach.

---

## Reflection

### How do I interpret user needs and implement them into a program? How does creating "user stories" help with this?

To interpret user needs, I start by finding out three things: what the user wants, why they want it, and the requirements to complete it. I then create a user story that is divided into these sections, which keeps requirements clear and leaves room to easily update the story if what the user wants is changed.

Creating user stories this way helps the team create what the user wants, not what we think they want. User stories also act as a reference point between the Product Owner, Product Tester, and Developers so there is an equal understanding of the requirements. User stories can then be changed later if needed, which directly keeps the entire team updated on what the user wants on a basic level. 

### How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?

I approach development in steps: understanding the main requirements, dividing them into different sections, developing each piece individually, and getting direct feedback on each piece. Going through this cycle for each task keeps my work consistent and prevents mistakes that could cost time and money later on.

In my future development work I plan to keep using these Agile practices:

- User stories: To keep requirements clear and originate from the user themselves.
- Backlog: So tasks are listed by priority, keeping myself and my team clear on what tasks we need to complete.
- Definition of done: To make sure everyone knows when a task can be considered completed and doesn't cause confusion later.
- Agile workflow tools: So items like backlogs and user stories are continually updated and synced between the entire team.

### What does it mean to be a good team member in software development?

Being a good team member is not just about knowing their own role, but also communicating clearly and asking questions instead of making assumptions. A team member should be reliable in all of these factors to not only make sure they are fulfilling their role but allowing their team to fulfill theirs as well. As a Scrum Master my role is to not command the team but assist them by facilitating Scrum events, making sure everyone is in constant communication, and removing roadblocks for the team.
